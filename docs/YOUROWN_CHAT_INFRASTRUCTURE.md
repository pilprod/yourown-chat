# Инфраструктура приложения YourOwn.Chat

Этот документ фиксирует минимальный контур, необходимый для запуска
пользовательских микросервисов из репозитория `yourown-chat-server`. Контур не
зависит от включения исполнителей агентов: остановка `agent-platform` не должна
останавливать вход пользователей, связи с рабочими пространствами и управление
платформой.

## Состав контура

| Объект | Реализация | Причина |
|---|---|---|
| База пользователей | Логическая база `yourown_chat_identity` в существующем Cloud SQL | Не создаёт второй оплачиваемый экземпляр |
| Вычислительный класс базы | Существующий `db-f1-micro`, зональный, диск 20 ГБ | Самый маленький уже используемый управляемый вариант |
| Учётные записи базы | Владелец схемы `yourown_chat_identity` и рабочая роль `yourown_chat_identity_runtime` без права изменения структуры | Процесс обслуживания запросов не может создавать или изменять таблицы и не имеет доступа к данным Mattermost и Temporal |
| Строки подключения | Раздельные секреты миграций и рабочей роли в Secret Manager | Пароли и повышенные права не попадают в манифесты и обычные секреты Kubernetes |
| Пространство Kubernetes | `yourown-chat-server` | Изолирует пользовательский сервер от `yourown-agents` |
| Прикладной чарт | `helm/yourown-chat` | Единица поставки пользовательского приложения |
| Вычислительный чарт | `helm/agent-platform` | Отдельно включаемые исполнители заданий |
| Поставщик личности | Keycloak `26.7.1` в отдельном пространстве `keycloak` | Общий вход, passkey и внешние поставщики для мобильных, настольных и веб-клиентов независимо от Mattermost |
| База Keycloak | Логическая база `keycloak` в том же минимальном Cloud SQL | Сохраняет изоляцию данных без второго оплачиваемого экземпляра |
| Ключ прикладного транспорта | Пустой контейнер `yourown-chat-transport-private-key` в Secret Manager, заполняемый вне Terraform | Закрытый X-Wing-ключ не попадает в HCL, план, состояние и исходный код |

В существующем экземпляре базы создаются новая база, роль владельца схемы,
рабочая роль и раздельные секреты их паролей и строк подключения. Новых
виртуальных машин, дисков или балансировщиков для базы не создаётся.

## Микросервисы

- `identity-migrate` выполняет повторяемые миграции для конкретного образа и
  завершает работу;
- `transport-api` является единственным публичным входом нативного клиента к
  собственным прикладным интерфейсам, расшифровывает X-Wing HPKE и передаёт
  запрос только разрешённой внутренней службе;
- `auth-api` публикует корневой договор `auth.yourown.chat`, проводит поток
  кода с PKCE и оставляет токены Keycloak внутри серверного контура;
- `identity-api` обслуживает прикладные сеансы YourOwn.Chat и проверенные связи
  с пользователями Mattermost; парольный вход наружу не публикуется;
- Keycloak проверяет первичную личность пользователя; `auth-api` проверяет
  краткоживущий токен через фиксированный внутренний адрес и выпускает
  непрозрачный прикладной сеанс, не сохраняя токен Keycloak;
- `identity-admin` управляет каталогом рабочих пространств через отдельную
  внутреннюю службу и не публикуется наружу;
- `control-api` предоставляет управление агентами и включается только после
  запуска Temporal;
- исполнители процессов и действий остаются в `helm/agent-platform` и могут
  быть уменьшены до нуля независимо от пользовательского сервера.

Каждый микросервис получает отдельную учётную запись Kubernetes и отдельную
учётную запись Google. `identity-migrate` получает только строку подключения
владельца схемы. `identity-api` получает только строку рабочей роли. `auth-api`
получает эту строку, собственный ключ шифрования состояния и открытую часть
сертификата Keycloak; ни один другой прикладной модуль не получает ключ.
`transport-api` получает строку рабочей роли для общей защиты от повторов и
собственный закрытый транспортный ключ; доступ к нему не имеет ни одна другая
служба.
`identity-admin` получает строку рабочей роли и внутренний административный
ключ. Доступ к ключу управления процессами имеет только `control-api`.

## Сетевые границы

В пространстве действует запрет входящего и исходящего обмена по умолчанию.
Разрешены только следующие направления:

| Источник | Назначение | Порт |
|---|---|---:|
| Входной контроллер | единый зашифрованный `/transport/v1` | 8084 |
| `transport-api` | точный частный адрес Cloud SQL | 5432 |
| `transport-api` | `auth-api`, `identity-api`, при включении `control-api` | 8083, 8081, 8080 |
| Входной контроллер | корневые маршруты `auth-api` | 8083 |
| `auth-api` | точный частный адрес Cloud SQL | 5432 |
| `auth-api` | Keycloak внутри кластера по TLS 1.3 | 8443 |
| `identity-api` | точный частный адрес Cloud SQL | 5432 |
| `identity-api` | Mattermost внутри кластера | 8065 |
| `identity-api` | Keycloak внутри кластера | 8080 |
| Входной контроллер | публичные пути `auth.yourown.chat/realms` и `auth.yourown.chat/resources` поставщика личности | 8080 |
| HCP Terraform | ограниченные административные пути `auth.yourown.chat/admin/realms` и `auth.yourown.chat/admin/serverinfo` для провайдера | 8080 |
| Keycloak | точный частный адрес Cloud SQL | 5432 |
| явно помеченный внутренний административный клиент | `identity-admin` | 8082 |
| `identity-admin` | точный частный адрес Cloud SQL | 5432 |
| `identity-migrate` | точный частный адрес Cloud SQL | 5432 |
| Mattermost | `control-api` | 8080 |
| `control-api` | Temporal | 7233 |
| серверные модули | служба имён | 53 |

Нативные маршруты пользователей, рабочих пространств, сеансов и управления
наружу напрямую не публикуются: они доступны только внутри зашифрованного
`/transport/v1`. Браузерный вход публикуется в корне `auth.yourown.chat`, но
чувствительный обмен кода по `/token` выполняется через `transport-api`.
Клиент получает только прикладной сеанс; собственные
регистрация и парольный вход не маршрутизируются. Для обмена действует
отдельное ограничение частоты и числа соединений. Внутренний административный
маршрут существует только в другом исполняемом файле и другой службе, поэтому
не может попасть во входной маршрут из-за нормализации пути. Службы имеют только внутренний тип
`ClusterIP`; отдельный облачный балансировщик не создаётся.

Консоль администратора поставщика личности не публикуется. Для отдельного стека
`keycloak` наружу открыт только машинный административный интерфейс областей и
сведений о сервере; он защищён учётными данными Keycloak и ограничением
частоты. Стек `keycloak` использует только провайдер `keycloak/keycloak` и
создаёт область `yourown-chat`, серверный клиент `yourown-chat-auth-broker`,
обязательный PKCE с SHA-256 и правила WebAuthn/passkey. Пользователи не являются
ресурсами Terraform. Секреты провайдера и внешних поставщиков не входят в
исходный код и хранятся в закрытых наборах переменных HCP Terraform.

Внутренний обмен `auth-api` с Keycloak выполняется по TLS 1.3 на порту 8443.
`auth-api` доверяет только сертификату, смонтированному в его пространство, и
проверяет имя `auth.yourown.chat`; сетевая политика разрешает этот порт только
между двумя нужными пространствами. Keycloak возвращает код в теле запроса
способом `form_post`, а журнал доступа на входном маршруте авторизации
отключён. Проверочная строка внутреннего PKCE хранится в базе как шифротекст
AES-256-GCM. Ключ `yourown-chat-auth-state-key` создаётся в Google Secret
Manager и доступен только служебной учётной записи `auth-api` через драйвер
CSI. В исходный код, значения Helm и секрет Kubernetes этот ключ не попадает.

Закрытый X-Wing-ключ создаётся отдельной процедурой после проверки изменений и
добавляется напрямую как версия секрета
`yourown-chat-transport-private-key`. Terraform создаёт только контейнер и
выдаёт право чтения отдельной рабочей личности `transport-api`. Драйвер CSI
монтирует значение как файл; передача закрытого ключа через переменную окружения
сервером запрещена. Открытый ключ и идентификатор `pilot-key-000001`
закрепляются в подписанной сборке нативного клиента.

Начальный машинный секрет самой службы Keycloak хранится в Google Secret
Manager. Стек `platform-gcp` читает только последнюю версию эфемерно и передаёт
её в поля без сохранения значения; секрет отсутствует в плане и состоянии
Terraform. Перед первым включением службы оператор создаёт первую версию
`keycloak-bootstrap-admin-client-secret` в Google Cloud и тем же значением
заполняет закрытый эфемерный набор переменных отдельного стека `keycloak`.
После создания постоянного административного клиента начальная учётная запись
отключается. Удаление её версии из Secret Manager выполняется вместе с
последующим исключением начального секрета из шаблона запуска, чтобы обычные
перезапуски и планы платформы не зависели от уже отозванного значения.

## Ограничение стоимости

Пространство ограничено десятью модулями, суммарным запросом 0,5 ядра и 1 ГБ
памяти. Для пилота запускается по одной копии `transport-api`, `auth-api` и `identity-api`; мигратор работает
только во время обновления. Основная прибавка к стоимости — использование уже
оплачиваемых узла GKE и экземпляра Cloud SQL, поэтому новый постоянный
оплачиваемый ресурс не добавляется.

## Поставка и отключение

Тег репозитория `yourown-chat-server` собирает и проверяет шесть отдельных образов,
после чего создаёт выпуск `yourown-chat` с обязательным подтверждением. Проверка
выпуска ожидает готовность `transport-api`, `identity-api`, `auth-api` и области Keycloak. Изменения самого чарта также
маршрутизируются в этот выпуск отдельным тегом платформы.

Для экономии нельзя уменьшать `identity-api` до нуля, если клиенты должны
входить в систему. Отдельно можно:

1. оставить Temporal выключенным — тогда `control-api` не создаётся;
2. остановить исполнителей агентов через выпуск `agents-pause`;
3. после пилота выключить самостоятельную регистрацию пользователей;
4. полностью убрать серверный контур переключателем
   `yourown_chat_server_enabled`, сохранив общую базу до осознанного удаления.

Порядок первого запуска: создать начальную версию секрета в Google Secret
Manager, применить `platform-gcp`, затем `app-gcp`, который создаёт в закрытых
пространствах две копии уже существующего сертификата: полную пару для
Keycloak и только открытую часть для `auth-api`. Развёртывание Keycloak на
первом шаге может ожидать этот секрет и не блокирует применение платформенного
стека. После появления сертификата нужно дождаться готовности Keycloak,
применить отдельный стек `keycloak`, создать тег
`yourown-chat-server`, подтвердить выпуск `yourown-chat-pilot`, проверить вход и
привязку пользователя Mattermost. Temporal и исполнители запускаются отдельным
этапом после успешной проверки пользовательского контура.
